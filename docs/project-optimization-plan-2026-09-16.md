# 项目优化方案

> 本文保留为初步分析记录。已合并至[项目统一优化实施方案](unified-optimization-plan.md)，实施范围、优先级及排期以统一版为准。补充校正：当前主课件生成入口已入库，但未接入本文讨论的审核重试函数，统一版已纳入修复。

编制日期：2026-09-16。依据：当前工作区源码、README 与已有改进路线图。本文是静态代码分析后的实施建议，未进行服务启动、性能压测或在线模型效果测试；指标为拟定验收目标，不代表当前实测结果。

## 一、总体结论

项目已具备 Vue 3 学生工作台、FastAPI 多服务、LangGraph 协调器、资源生成、答疑、学习路径、答题评价和报告等完整功能基础。下一阶段应优先保证身份校验、执行状态、生成审核和学习反馈可信，再优化延迟、检索质量与维护成本。

建议保留 Python 主运行链路，暂缓扩大 Java 迁移范围。先完成“画像 → 路径 → 课件 → 练习 → 评价 → 路径调整”这一条可验证闭环。旧路线图可作为方向参考，但部分描述需要修正：报告服务已有真实答题统计，掌握度已有难度与用时因素，不能再笼统描述为“报告完全依赖 LLM”或“没有行为反馈”。

## 二、按优先级实施

### P0：修复可信性与正确性，建议 1–2 周

| 优化项 | 当前源码依据 | 实施方案 | 验收标准 |
|---|---|---|---|
| JWT 校验失败时拒绝访问 | `common/security/auth.py` 的 `decode_access_token` 在缺少 jose 时只解码载荷，没有验证签名与过期时间；密码哈希也有 SHA-256 降级 | 生产启动时检查必要依赖；删除不安全认证降级；校验异常统一转换为 401；若存在旧哈希账号，设计明确迁移流程 | 伪造、篡改、过期、格式错误令牌均无法访问；缺依赖时服务启动失败且错误明确 |
| 补齐生成与编排接口权限 | `agents.py`、`resources.py` 路由未注入当前用户依赖；agent-service 注册这些路由时也未设置全局认证依赖 | 复用 `common/dependencies.py`；学生身份取自令牌；教师按班级关系授权；校验资源和任务归属；限制客户端指定智能体的范围 | 未登录调用返回 401；学生 A 无法以学生 B 身份生成资源或执行任务；角色矩阵测试通过 |
| 修复审核重试闭环 | `resource_generation.py::_audit_and_retry_courseware` 重试替换 `primary` 后未更新用于审核的 `content`；创建的重试模型未用于实际生成；重试耗尽仍返回 `primary` | 每次审核当前候选；显式传递模型参数；检查拒绝原因是否进入实际提示词；失败返回明确状态；同步修正主版本与 variants 的内容一致性 | 首次拒绝后确实审核新版本；连续拒绝不会显示为已通过；主课件和推荐变体一致 |
| 区分审核通过与不可用 | `audit_service.py` 在调用异常或解析失败时可能返回通过；目前只抽取课件开头和前三道题 | 使用 `passed / rejected / unavailable` 三态；结构规则检查覆盖全部题目；审核不可用内容标记为待审核或草稿，禁止误标为通过 | 注入超时、非法 JSON、后半段错误等案例，状态正确且可追溯 |
| 分离同步执行与队列投递 | `coordinator.py::run` 先执行含投递的图，再在 execute=true 时本地执行；`_resolve_conflicts` 根据选中智能体就标记 success | 显式选择同步或异步模式；增加 task_id、幂等键及状态机；投递完成仅为 queued，执行完成才为 succeeded | 同一请求只触发一次业务执行；投递成功不会被当作学习内容生成完成 |

说明：在 `common`、`services` 中未检索到消费者确认与消费循环实现，因此“消息已重复消费”不能视为已证实故障。但现有双路径在未来接入消费者时会带来重复执行风险，应先定义清楚。

### P1：保证学习反馈有效，建议第 2–3 周

**1. 校准掌握度更新。**

`services/evaluation_service/app/services/profile_updater.py` 使用 0–100 分制，却以 ALPHA=0.2 更新分数。最高难度、用时为零且答对时单次最多增加 0.24 分；用时达到或超过 max_time 时，无论对错均不改变分数。这会削弱持续练习对路径调整的影响。

先统一分数量纲，明确正确性、部分得分、难度与用时的作用。用时仅作为有限的辅助信号，不应消除答错证据。用固定答题序列校准：连续正确应明显提升，连续错误应下降，慢速正确和快速乱猜应可区分。随后再根据真实数据评估是否引入知识追踪模型。

复习调度与掌握度估计应分开：复习间隔不能直接替代掌握度模型。没有离线验证前，不承诺学习效果提升。

**2. 将画像历史与汇总拆开。**

当前掌握度 JSON 持续追加 history，并重算历史统计。建议以答题记录作为事实来源，画像仅保存聚合值、有限近期窗口、证据数量、更新时间与规则版本。更新增加版本检查或行级并发控制，避免并发提交覆盖彼此结果。

验收：重复提交不重复计分；并发提交不丢记录；可从答题事实重建画像；迁移前后历史报表一致。

**3. 增强路径调整的可解释性。**

保留现有路径能力，增加调整理由、触发证据、先修知识点与预计学习时长。区分自述偏好、测评结果和行为证据，避免一次对话覆盖长期学习表现。报告中的数值继续由程序统计，LLM 负责解释与建议，所有建议可追溯到答题证据。

验收：用户可看到“为何推荐”；缺乏数据时明确显示证据不足；LLM 无法篡改正确率、答题数等统计事实。

### P1：提高运行可靠性与响应体验，建议第 3–4 周

**1. 为长任务建立可恢复执行机制。**

`web-app/src/api/http.ts` 对全部请求统一设置 120 秒超时。先测量生成、审核、数据库等分阶段耗时，再确定哪些接口迁移到任务模式。普通查询使用较短超时；长生成返回任务标识，支持查询进度、失败原因和结果恢复。刷新页面后可以继续查看任务，不依赖页面内存。

先实现可靠轮询，再按体验需要增加 SSE。进度展示使用真实阶段，如“检索中、生成中、审核中”，不伪造百分比。

**2. 给消息链路补齐可靠性。**

`common/messaging/rabbitmq.py` 已声明持久队列和持久消息，但没有发布确认；缺少 pika 时写入本地 JSONL，未在所查目录发现完整回放机制。

短期让同步主流程不依赖消息投递。异步正式启用前增加发布确认、消费者幂等、有限重试、死信处理与任务状态持久化。数据库写入和事件发送需要一致性时，采用事务发件箱。开发降级队列明确标记为开发用途，并提供积压检查。

验收：模拟消息重复、服务重启和队列不可用，已受理任务不会静默消失；同一答题结果只影响画像一次。

**3. 统一模型调用预算。**

`llm_factory.py` 是按配置选择单一供应商，不能据此认为已经实现运行时故障切换。增加统一调用封装，记录模型、阶段、耗时、调用次数和用量；设置请求总截止时间与最大调用次数。只对可恢复错误有限重试，避免底层和业务层重试相乘。供应商熔断与切换在实测需要时引入。

继续默认生成一份课件；其他风格按需生成。缓存键至少包含知识点、画像版本、提示词版本、模型与知识库版本；用户私有内容必须隔离。

### P2：提升资源与检索质量，建议第 4–5 周

`rag.py` 使用固定的 education_resources 集合；标签过滤在扩大召回后进行，未命中时会退回未过滤结果。建议：

1. 为知识点统一 ID，为资料增加来源、学科、版本、内容哈希及入库时间。
2. 将必须满足的学科约束与偏好标签区分开，避免跨学科回退。
3. 建立可切换的索引版本，导入后验证再切换，保留上一版本用于回滚。
4. 建立小规模人工标注检索集，先比较现有检索与关键词、向量混合检索，再决定是否增加重排。
5. 回答返回可核对的引用；无可靠来源时明确标记。召回距离不能直接等同于答案正确概率。

生成质量采用“确定性规则 + 模型审核 + 教师抽检”：规则检查字段、答案选项、结构和引用；模型检查相关性与讲解合理性；教师对固定样本评价概念正确性、例题质量、难度和可学性。把资料和学生输入视为不可信内容，不能让它们改变系统规则或授权范围。

验收：至少建立 50 条检索标注样本与 30 份课件评价样本；同一数据集对比前后命中率、教师评分和单位合格内容成本。样本规模不足时仅报告趋势。

### P2：降低维护与交付成本，建议第 5–6 周

- **渐进拆分页面。** 当前 ResourceView 约 1324 行、QaView 约 1265 行、ReportView 约 994 行。优先抽离请求与任务状态、图表展示、资源筛选等职责，不按固定行数机械拆文件。已有学生路由懒加载应保留，其他页面是否调整以构建分析为依据。
- **固定接口契约。** 从后端 OpenAPI 生成或校验 TypeScript 类型，统一错误响应和任务状态，减少页面层猜测响应字段。
- **建立持续集成。** 已有较多后端测试；本次未发现 .github/workflows。接入核心单元测试、接口冒烟、前端构建与迁移检查，新增一条学习闭环端到端测试。
- **统一运行说明。** README 要求 Python 3.12+，pyproject 为 3.11+；明确最低支持版本和实际 CI 版本。整理启动依赖、端口与配置检查。
- **增加可观测性。** 使用贯穿请求、任务、智能体、模型调用的 trace_id；记录错误类型、重试与审核结果；日志避免保存令牌和完整学生隐私信息。将存活检查与依赖就绪检查区分开。

## 三、建议交付节奏

按 2 名开发人员配合兼职测试/教学评审估算，完整实施约 4–6 周；这是排期估算，需结合现有测试结果重新确认。

| 阶段 | 交付成果 | 进入下一阶段的条件 |
|---|---|---|
| 第一阶段 | 身份校验、对象授权、审核重试、执行模式修复 | P0 回归用例全部通过 |
| 第二阶段 | 掌握度校准、幂等答题、画像聚合与证据解释 | 固定学习轨迹测试通过，报告统计一致 |
| 第三阶段 | 持久任务、消息恢复、调用预算与进度展示 | 重启恢复和故障注入测试通过 |
| 第四阶段 | 检索评估、版本化、页面拆分、CI 和交付文档 | 学习闭环端到端验证通过 |

若仅有一周，优先交付 P0 修复、掌握度公式测试与一条闭环冒烟验证。暂缓 Java 全面迁移、复杂事件总线、通用插件平台和多版本默认生成。

## 四、验收指标与验证边界

| 维度 | 建议验收目标 | 测量方式 |
|---|---|---|
| 权限 | 既定未授权与跨用户访问用例全部拒绝 | 角色及对象归属矩阵测试 |
| 审核 | 拒绝、不可用、通过三态不混淆 | 固定模型替身与故障注入 |
| 执行 | 重复请求、重复消息不产生重复业务结果 | 并发与重放测试 |
| 学习反馈 | 对错、部分得分、慢答、超时的预期行为明确 | 固定答题序列及教师复核 |
| 性能 | 在相同模型与负载下，生成 P95 延迟较基线降低 20%，作为初期目标 | 分别记录排队、检索、生成、审核时间 |
| 成本 | 单位合格课件的模型用量较基线降低 15%，质量不下降，作为初期目标 | 按通过审核且抽检合格的资源统计 |
| 恢复 | 已持久受理任务重启后可查询并恢复或明确失败 | 中断与重启演练 |

性能和成本目标必须先建立基线；如质量、供应商延迟或预算约束冲突，重新调整目标，不能通过跳过审核达标。本方案未执行测试，不对现有测试是否通过作结论。

## 五、第一批可直接创建的开发任务

1. 删除 JWT 非验证降级，补齐异常到 401 的转换和认证回归测试。
2. 给协调器、资源生成等入口补认证、对象归属校验与允许的智能体清单。
3. 修复课件重试审错版本和耗尽后误返回，补审核三态与变体一致性测试。
4. 将 execute=true 的同步调用与队列投递分开，定义任务状态语义。
5. 为掌握度建立固定行为测试，校准量纲及超时行为。
6. 建立调用耗时、审核结果和任务状态基线，再决定异步迁移范围。
