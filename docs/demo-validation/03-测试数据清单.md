## 5. 学习证据（学情分析的数据来源）

学情**不是**写进数据库的标签，而是真实作答 → 服务端判分 → 画像递推 → 接口汇总的反算结果。
脚本侧只准备"能被证据层接纳的题目"，一行答案都不写。

### 5.1 证据层的三条硬过滤

| 过滤条件 | 含义 | 演示题库的处理 |
| --- | --- | --- |
| `content.generated_for_user_id` 为空或等于当前学生 | 专属生成题不能被别的学生复用 | 复制出公共演示题，去掉该字段 |
| `classification_status != pending` | 未归类归因的题不算证据 | 走 `/evaluation/submit`（已存在的 Exercise 行）提交，不会被标成 pending |
| `evaluation_json` 不含 `evidence_excluded`/`test_data`/`evidence_source in {demo,test,synthetic}` | 防止脏数据污染学情 | 判分链路自动写入 `scoring_status=completed`、`evidence_source=objective_or_rule` |

> 关键差别：若用 `exercise_id` 指向**不存在**的题目，`_upsert_exercise` 会新建并打上
> `generated_for_user_id` + `classification_status=pending`，证据层随即把它排除——这正是早期
> "有 256 条作答却显示暂无数据"的根因。现在学生只答**题库里已存在的演示题**，天然满足过滤。

### 5.2 作答是怎么发生的

```
剧本侧（决定学生"想选哪个选项"）        系统侧（决定对错）
──────────────────────────────        ──────────────────────────────────
excellent  normal  struggling  pending → POST /evaluation/batch_submit
→ 答对就用标准答案                      → _compare_objective_answer(user_answer, exercise.answer)
→ 答错就真选一个干扰项 / 判断取反 /      → is_correct（我们不传，也不改）
  填空写"不确定（未掌握该知识点）"        → ProfileUpdater 递推 mastery
                                        → load_evidence → insights / teaching-analytics
```

提交总数 340（34 人次 × 10 题），实际新增 330 条：跨班选修且两班同知识点的学生
（`demo_s05` 同属两个数据结构班）第二次提交被 `client_request_id` 幂等退回 10 条，未重复计分。

## 6. 时间策略（避免演示过期）

- 作业与打卡的相对时间在**首次创建时冻结**：重复执行 `seed` 不会刷新时间，也不会重复建数据。
- 若环境闲置多日导致"可交互"任务全部过期，执行：

```bash
python scripts/demo_teaching_dataset.py --db <runtime.sqlite> --action refresh
```

该命令只把仍处于 `published` 状态的作业截止时间、打卡窗口向当前时间对齐，不新建记录、不改已截止的历史数据。
