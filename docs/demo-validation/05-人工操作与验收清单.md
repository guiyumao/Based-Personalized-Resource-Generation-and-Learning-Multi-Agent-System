## 验收 8：学情分析使用真实数据（含差异化）

### 8a 教师端「学生洞察」

| 项 | 内容 |
| --- | --- |
| 账号 | `demo_zhangming`（密码 `Demo@2026`） |
| 入口 | `/teacher/students`（分析与任务 → 学生洞察） |
| 操作 | 选择「数据结构 · 软件工程1班」，点「刷新洞察」 |
| 预期 | 8 张学生卡片，掌握度**互不相同且都在 1~100 之间**，错题数与正确相反（正确多则错题少） |

本轮真实跑出来的结果（**不要把下面的数字当成"必须等于"的标准**，每次重跑会因作答不同而略有差异）：

| 账号 | 画像 | 本轮掌握度 | 错题 |
| --- | --- | --- | --- |
| `demo_s01` / `demo_s03` | 优秀 | 90 / 90 | 1 / 1 |
| `demo_s02` / `demo_s04` / `demo_s05` | 普通 | 70 / 80 / 60 | 3 / 2 / 4 |
| `demo_s06` / `demo_s07` | 学习困难 | 30 / 40 | 7 / 6 |
| `demo_s08` | 待处理业务 | 30 | 7 |

判定要点应改成三条：
1. **不是全空**（每条都有值）；
2. **存在梯度**（至少两种不同掌握度）；
3. **顺序合理**（优秀画学生的正确题数多于困难画像）。

### 8d 交叉核验

| 项 | 内容 |
| --- | --- |
| 核验方式 | 用 SQL 直接算该班学生正确率，应与页面掌握度量级一致（同向） |
| 语句 | `select u.username, round(avg(a.is_correct)*100) from answer_records a join users u on u.id=a.user_id join exercises e on e.id=a.exercise_id where u.username like 'demo_s0%' and e.assistant_operation_key like 'demo-evidence-%' group by u.username;` |
| 溯源 | 每条 `answer_records` 的 `evaluation_json.evidence_source` 应为 `objective_or_rule`，`scoring_status` 为 `completed`——说明它是判分链路写出来的，而不是脚本塞进去的 |

> 数据库原理 / Java / Python / 软件工程四门课没有公共题库，其学情为 0 是**真实情况**（脚本会把这些班列入 `skipped`），不得为了让页面好看而伪造题目。

## 验收 10：重复执行不产生重复数据

| 项 | 内容 |
| --- | --- |
| 操作 | 再次执行 `--action seed` |
| 预期 | 输出 `created: {}`；教师、学生、班级、课程、作业、签到数量不变 |

## 验收判定

- 上述 10 项全部符合预期 → 演示环境可用于答辩与演示。
- 任一项不符合时，先执行 `--action check` 看一致性是否被破坏，再用 `--action reset --yes` + `--action seed` + 角色用例三步重建。
- 重建会删除 `demo_%` 账号及其全部业务数据，不影响真实账号。
